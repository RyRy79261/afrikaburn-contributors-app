_Ryan, 25 Jul 2026. Every account gets an in-app notification stream; the org gets a
bulletin system to broadcast to audiences. "Your camp has been approved", "Wrangler
assigned", "Attention: ticket resale window opens" — personal events and broadcasts,
one inbox._

## Model

Two kinds, one inbox:

- **Notification** — personal, event-generated, per-account. Sources: registration
  status changes (submitted/under review/changes requested/approved), wrangler
  assigned, role/officer assignment + acceptance requests, questionnaire released to
  you (blocking ones flagged), membership events (invite accepted, lead transfer),
  supplier onboarding confirmations (deposit received, briefing confirmed, standing
  changed), account security events (mirrors the security-events feed).
- **Bulletin** — org-authored broadcast to an **audience** (reuses the questionnaire
  audience machinery verbatim: all current burners / camp leads / registered camp
  leads / MV leads / art leads / grant requesters / suppliers / registered <role>).
  A bulletin lands in each recipient's inbox as a notification of kind `bulletin`
  and also exists as a standalone readable page (deep-linkable).

Schema (rides existing spine):

- `bulletins` (edition_id, title, body_md, audience — same enum/shape as
  questionnaire audiences, created_by, published_at, pinned bool)
- `notifications` (recipient account id, kind, title, body?, link, bulletin_id?,
  created_at, read_at) — append-only; read_at set on open; "mark all read".
- Unread count = cheap query; no per-device state.

Laws:

- **Fewer-forms**: notifications are generated by events that already exist — no new
  data collection. Bulletin compose = title + body + audience + optional pin. Nothing else.
- **Never-payments**: no payment notifications exist.
- **Privacy**: notifications never leak private fields into previews; supplier
  standing changes are visible only to that supplier; org-internal events never reach
  participant inboxes.
- **Email**: Resend digest for unread (max 1/day) + immediate email ONLY for blocking
  questionnaires and registration decisions. In-app is the source of truth
  (zero on-site connectivity — anything on-site queues for lazy sync, same as
  everything else).

## Surfaces

**Every app header (all three apps, desktop + mobile):** bell icon + unread-count
badge in the right cluster. Opens the notification panel (desktop dropdown; mobile
full page).

- **Notification panel** (dropdown card study): last ~6 items, unread dot per item,
  "Mark all read", "All notifications →".
- **/notifications** (participant, org, supplier — one shared pattern, app accent):
  filter tabs (All / Unread / Bulletins), grouped by day, item = icon-by-kind +
  title + time + unread dot; bulletins expandable/linked. Empty state.
- **Bulletin view** (participant): pinned banner on dashboard for pinned bulletins +
  full bulletin page (title, body, published date, "From AfrikaBurn").
- **Org console → Bulletins** (new section in nav):
  - list: sent + drafts, audience chip, sent date, read-rate bar (n of m read)
  - compose: title, body (markdown), audience selector (same component as
    questionnaire audiences), preview-as-recipient card, Publish + pin toggle.
    Blocking-style banner clarifies bulletins are informational — anything requiring
    action should be a questionnaire (keeps the fewer-forms law: bulletins never
    collect data).

Notification examples (canonical demo copy):

- 🎉 "Mad Hatters has been approved — placement application is now open" (link → camp)
- 🧑‍🚒 "Fire Safety Officer registration accepted — AfrikaBurn can now contact you"
- 📋 "New questionnaire from AfrikaBurn: Build week availability — REQUIRED, blocks
  registration" (accent-flagged)
- 🧭 "Sipho from the theme camp leads team is now your wrangler"
- 📣 Bulletin: "Ticket resale window opens 1 March — Quicket only, watch for scams"
- 📦 (supplier) "Deposit received — confirmed by AfrikaBurn" / "Standing changed to
  In Good Standing"

  camp context exists (Camp Dashboard); Landing stays marketing-clean.
